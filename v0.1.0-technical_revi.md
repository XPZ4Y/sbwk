# SBWK (Sleepy Bot with Keys) — Code Explanation & Limitations

## What This System Is

SBWK is a **self-hosted observability + AI-assisted incident diagnosis** stack. A reverse-proxy "edge" sits in front of your application, detects anomalies (5xx, 4xx, slow responses, upstream failures), ships incidents to an "Agent Core" that investigates dependency health and greps the codebase, then produces a root-cause hypothesis with suggested fixes and escalates to a human when confidence is low.

It's five Node.js services, all **zero-dependency** (native `node:http` only), orchestrated by Docker Compose.

---

## Architecture Walkthrough

### 1. `services/middleware` — the Edge (port 8080)
The reverse proxy. Clients hit `:8080`; traffic is proxied to `TARGET_SERVER_URL` (default `:8000`).

- **`detector.mjs`** — pure functions:
  - `classifyStatus(500, 500)` → detect, `server_error`. `classifyStatus(404, 500)` → no detect. Threshold configurable.
  - `DispatchThrottle` — dedupes incident dispatch by `method+path+status` within a cooldown (default 15s) so a flapping endpoint doesn't spam the agent.
  - `buildIncident` — normalizes the anomaly into an incident object (splits query, rounds duration).
- **`server.mjs`**:
  - Resolves the proxy target *per request* (so onboarding can re-point it live).
  - Buffers up to `RESPONSE_SAMPLE_BYTES` (2 KB) of the response to attach to the incident.
  - Detects `slow_response` if `DETECT_SLOW_MS` exceeded; maps `ETIMEDOUT` → 504/timeout, other proxy errors → 502/upstream_unreachable.
  - Fires incidents **fire-and-forget** to Agent Core; logs `anomaly_detected` and `incident_dispatched`.
  - Admin routes (`/_sbwk/status`, `/incidents`, `/config`) are bearer-token protected; `/health` is open.

### 2. `services/agent-core` — the Brain (port 4200)
The orchestrator. `POST /incidents` accepts an incident (202 async, or `?wait=true` synchronous).

- **`investigate.mjs`** — `createInvestigator` with injected deps (testable):
  1. In parallel: query the Connector (`investigateDependencies`) and grep the codebase (`inspectCodebase`).
  2. `reason()` → analysis (LLM or heuristic).
  3. `decideEscalation` — escalates if confidence < threshold, severity critical, connector unreachable, a dependency is unreachable, app server itself unreachable, or the path has failed ≥3 times.
  4. `store.attachAnalysis`, then `notifyEngineer` if escalating.
- **`reason.mjs`**:
  - `deriveDependencyFindings` — collapses per-check evidence into a worst-status-per-service view, extracting human-readable signals (`connection pool 100% used`, `error rate 42%`, …).
  - `heuristicReason` — a decision tree: unhealthy DB → "database degradation", unhealthy external API → "third-party outage", auth → auth degradation, upstream-unreachable → server down, 404 → routing issue, slow → perf regression, code match → code bug, else "insufficient evidence". Correlates recent GitHub commits against the path words and can `unshift` a "review commit X" fix.
  - `groqReason` — optional live LLM (Groq, OpenAI-compatible) with a strict system prompt ("read-only", "don't invent facts about healthy deps", JSON-only), validated before acceptance; **falls back to the heuristic** if the key is missing, call fails, or output is malformed.
- **`codebase.mjs`** — read-only grep: derives keywords from path segments + error vocabulary, walks the repo (skipping `node_modules`, `.git`, etc., files >256 KB), scores files by keyword hit count and best-line density, returns the top N snippets with line context. Never executes code.
- **`store.mjs`** — bounded in-memory `IncidentStore` (default 200) with optional JSON persistence, `recurrenceForPath` for the recurring-failure signal, and `contextSummary()`.
- **`notify.mjs`** — always logs an `engineer_notification`; optionally POSTs to `NOTIFICATION_WEBHOOK_URL` (Slack-style `{text}` payload).
- Config defaults: `DRY_RUN=true`, `AUTO_ROLLBACK=true`, `AGENT_MODE=mock`. Production refuses to boot with default tokens.

### 3. `services/agent-connector` — the Hands (port 4100, internal only)
Read-only dependency diagnostics. Exposes 9 tools (3 services × health/metrics/logs) in native + OpenAI function-calling formats.

- **`adapters.mjs`** — `serviceChecks` map, tool definitions, `inspectService` (live: `fetch` with timeout, contract validation, error normalization to `TIMEOUT`/`CONNECTION_FAILED`/`CONTRACT_VIOLATION`/`NOT_CONFIGURED`), and `investigateServices` (bounded concurrency, summary counts).
- **`mock.mjs`** — three scenarios (`normal`, `database_failure`, `external_api_failure`) that mutate health/metrics/logs realistically (100% pool, 2400ms queries, HTTP 503, 27 timeouts…). Scenario is runtime-switchable — this is how the demo works with zero external infra.
- `POST /connector/config` lets the control plane push live base URLs/tokens/paths at runtime.

### 4. `services/control-plane` — Onboarding UI + API (port 4300)
Serves a static UI and makes each onboarding step real over HTTP:

- **Step 01 Gateway** — `applyGateway` POSTs `targetServerUrl` to the middleware; `/api/gateway/check` does a real reachability probe.
- **Step 02 External access** — `checkReachability` does an HTTP GET (any status = reachable) or, for non-HTTP schemes (`mongodb+srv`, etc.), a **DNS lookup** as a proxy for reachability. `applyExternal` pushes HTTP endpoints to the Connector.
- **Step 03 Codebase** — `fetchGitHubRepo` calls the real GitHub API (`/repos/:o/:r` + `/commits?per_page=5`), stores metadata + last 5 commits, pushes them to Agent Core. Token is stored but **redacted** from API responses (`store.redacted()`).
- **Step 04 Safety** — pushes `dryRun`, `autoRollback`, `escalationThreshold` to Agent Core.
- **Monitoring switch** — `/api/monitoring/start|stop` flips `MONITORING_ACTIVE` in Agent Core; when paused, incidents are recorded but not investigated.
- **`/api/incidents`** proxies the live feed from Agent Core.

### 5. `services/dummy-server` — the Target App (port 8000)
A tiny stand-in backend. `/users` (DB), `/external` (third-party), `/status/:code` (httpbin-compatible), `/delay/:s`, and `POST /_control` to flip `normal|database|external` failure modes at runtime. Replaces the ~200 MB httpbin image.

### Tests
Pure-function unit tests across all four services: detector classification/throttle, codebase keyword derivation and file scoring, heuristic reasoning for each branch, investigator escalation logic, connector tool contract, control-plane URL parsing and reachability.

## Limitations

### Correctness / functional
1. **No real fix execution.** By design — but `AUTO_ROLLBACK`, `DRY_RUN`, and `MONITORING_ACTIVE` are *policy flags only*. Nothing in the codebase ever rolls back, restarts, or remediates. The "auto-rollback" toggle is cosmetic today.
2. **Codebase search is naive substring matching.** No AST, no symbol resolution, no call-graph. `scoreContent` just counts keyword hits per file/line. It will miss renamed functions, indirect callers, and minified/transpiled code, and can surface false positives (`"users"` matches comments).
3. **Only HTTP(S) dependencies are actually probed.** Non-HTTP URLs (`mongodb+srv`, `postgres://`, `redis://`) get a DNS lookup only — no protocol handshake — so "reachable" can be true while the DB is down. `applyExternal` explicitly *skips* pushing non-HTTP endpoints to the Connector, so a Mongo endpoint in onboarding never reaches live diagnostics.
4. **Reasoning is heuristic by default.** `AGENT_MODE=mock` uses hardcoded confidence numbers (0.82 for unhealthy DB, etc.) tuned to the mock scenarios. It looks impressive on the demo but is brittle on real traffic shapes it wasn't tuned for.
5. **Commit correlation is crude.** It lowercases commit messages and checks whether any path word is a substring. A commit "fix user auth" matches `/users`; a commit "add /users endpoint" also matches — but so does "update user docs". No diff inspection despite the suggested fix saying "inspect its diff."
6. **`deriveKeywords` is a fixed vocabulary.** `["database","pool","timeout","connection","auth","token","econnrefused","null","undefined","query"]` — anything outside this list (e.g. `redis`, `s3`, `kafka`, `rate_limit`) won't boost codebase matching.
7. **Contract validation in the Connector is minimal.** It checks `status` enum, `metrics` object, `logs` array — not shape or types within. A live service returning `{status:"healthy", checks:null}` passes.
8. **Mock `structuredClone(health[service])` then mutating `sample.checks`** — fine, but if a service entry were missing it'd throw; only 3 services exist so it's contained.

### Reliability / operability
9. **Fire-and-forget dispatch.** The middleware logs `incident_dispatch_failed` but never retries. A short Agent Core outage = dropped incidents. The throttle's dedupe window (15s) can also suppress a genuinely distinct second failure on the same path/status.
10. **Cooldown state is process-local.** `DispatchThrottle.last` is an in-memory `Map`. Run multiple middleware replicas and each dedupes independently → duplicate investigations. No distributed lock.
11. **`IncidentStore` is in-memory + optional single-file JSON.** `persist()` rewrites the whole array on every mutation (O(n) per write, synchronous `writeFileSync` blocking the event loop). No locking → concurrent replicas clobber the file. No TTL/retention beyond the `max` ring.
12. **`MAX_CONTEXT_INCIDENTS` default 200** caps context — recurrence detection silently forgets beyond that.
13. **Config is mutable global state.** `POST /connector/config` and `/config` mutate the exported `config` object at runtime. No validation of pushed `paths` (an attacker with the token could set `paths.logs = "/../../etc/passwd"`-style — `new URL(path, baseUrl)` would normalize, but no allowlist). No audit log of who changed what beyond one log line.
14. **No rate limiting anywhere.** Middleware proxies unbounded traffic; Agent Core and the Connector have no per-token throttles. An attacker who learns the bearer token can hammer `POST /incidents` and force expensive LLM calls.
15. **Tokens in prod are only checked for the `development-only` prefix** at boot. A weak but non-default token passes silently. No rotation, no scopes, single shared token per service.

### Security
16. **Response samples are captured and stored.** Up to 2 KB of upstream response body (potentially PII, tokens, or error internals) goes into the incident record, persisted to disk and sent to Groq in live mode (truncated to 800 chars). No redaction/masking layer.
17. **Incident payloads are passed to the LLM verbatim** (`JSON.stringify(evidence)`) including `userAgent`, `clientIp`, `responseSample`. Prompt-injection surface: a malicious upstream response containing "ignore previous instructions" enters the LLM prompt. The system prompt says "use ONLY the evidence," but there's no output sanitization beyond JSON-shape validation — and `suggestedFixes[].file` is rendered in the UI as a link.
18. **`fetchGitHubRepo` stores the GitHub token in `state.codebase.token`** on disk (persisted in `onboarding.json`). `redacted()` hides it from the browser, but it's plaintext at rest in the data dir; no encryption, no KMS.
19. **No CSRF protection on the control-plane UI endpoints.** They're bearer-less (the UI is served by the same origin and the API assumes local trust). Any page in the developer's browser could POST `/api/gateway` with `targetUrl` pointing at an attacker's server — turning the developer's own middleware into an SSRF pivot.
20. **`checkReachability` is an SSRF primitive.** It fetches any user-supplied URL server-side. Combined with (19), this is a classic internal-network reconnaissance gadget. No allowlist, no private-IP blocking.
21. **`applyConfig` in Agent Core accepts arbitrary `codebase.commits` objects** — no schema check. A caller can inject a fake "recent commit" whose `url` points anywhere, and `heuristicReason` will surface it as `fix(...).file` in the UI.
22. **`X-Forwarded-For` is trusted blindly** (`fwd.split(",")[0]`) — client-controlled `clientIp` ends up in incidents and LLM prompts.

### Robustness
23. **Agent Core `POST /incidents` with `?wait=true`** awaits the full investigation inline — a slow LLM (20s timeout) blocks the HTTP response. The middleware doesn't use `wait=true`, but any caller could.
24. **`groqReason` has no retry/backoff** and a single 20s abort; transient Groq 429s silently degrade to heuristic without any signal in the analysis (`mode` becomes `mock`, which is confusingly also the default).
25. **Heuristic confidence is not calibrated.** `0.82` isn't derived from anything. The escalation threshold default in code is `0.5`, in the control-plane store `0.8`, in Compose `${ESCALATION_CONFIDENCE_THRESHOLD:-0.8}` — three different defaults for the same knob. Confusing and easy to mis-operate.
26. **`validateIncident` requires exact string fields** but the middleware sends `query`/`responseSample`/`error` optionally — fine, but any future producer that omits `source` or uses `uri` instead of `path` is rejected with a generic message.
27. **The dummy server's `/delay/:s` caps at 10s** and the middleware's `PROXY_TIMEOUT_MS` is 30s, so `DETECT_SLOW_MS=2000` + `/delay/3` works — but there's no test covering the slow-response path end-to-end (only `classifyStatus`).
28. **`recurrenceForPath` scans all records linearly** on every investigation; with `max=200` fine, but it's O(n) per incident.

### Design / product
29. **No persistence of *why* a suggested fix was chosen beyond the free-text `reasoning` string.** No structured evidence graph an engineer can audit.
30. **The "codebase" is the mounted repo at `/codebase:ro`** — the agent greps *whatever repo you mounted*, including SBWK's own source if you follow the default Compose volume `./:/codebase:ro`. In the demo that means the agent can "find" middleware code and report it as the app's bug.
31. **UI is a single static HTML file** served by the control plane; there's no auth on the UI itself (only the downstream calls are token-gated), so exposing port 4300 on a shared host leaks onboarding state (`hasApiKey: true`, repo name, commit list).
32. **`docker-compose.httpbin-lite.yml`** documents that go-httpbin lacks `/_control`, `/users`, `/external` — so switching to it **breaks the entire DB/external failure demo path**; only `/status/:code` and `/delay` remain. The README doesn't call this out.
33. **`apply.mjs`'s `applyExternal` builds `paths.logs` from `new URL(endpoint).pathname`** — so the "logs" path is literally the health endpoint's pathname. That's a guess, not a discovery; the Connector will happily `GET /health` and validate it as "logs", fail `Array.isArray(data.logs)`, and report `CONTRACT_VIOLATION`. No feedback loop to the onboarding UI that the mapping is wrong.
34. **No test exercises `apply*.mjs` or the control-plane `server.mjs` HTTP surface** — only `checks.mjs` parsing/reachability. The actual "make onboarding real" code is untested.

### Summary

The architecture is clean and the zero-dependency choice keeps the deploy surface tiny and auditable. The demo path (mock scenarios + heuristic reasoner + throttled dispatch) is coherent and well-tested at the unit level.

The **main gaps** are: (a) the "safety" flags are inert, (b) non-HTTP dependencies are effectively unobservable, (c) the control plane is an unauthenticated SSRF surface with plaintext tokens on disk, (d) LLM/response-sample handling has no redaction or injection defense, and (e) several consistency bugs (three escalation defaults, codebase mount overlapping SBWK itself, "logs" path guessing). None are fatal for a local demo; most would need addressing before this touched real production traffic.
